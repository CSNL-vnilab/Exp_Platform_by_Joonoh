# Lab 자체 DB — 구조와 기록·조회 방식

이 문서는 본 플랫폼의 Supabase PostgreSQL 데이터베이스가 **무엇을** /
**어떻게 기록하고** / **어떻게 다시 꺼내올 수 있는지** 를 설명합니다. 이전
워크플로우 그림들과 같이 읽으면 시스템의 모든 동작이 한 DB 안에서 어떻게
설명되는지 보입니다.

---

## 0. 큰 그림

한 실험을 중심으로 다섯 가지가 서로 연결되어 보관됩니다.

| 무엇을 보관하나 | 핵심 항목 |
|---|---|
| **실험 자체** | 제목·기간·정원·세션 수·위치·코드 경로·저장 경로·체크리스트·자동 코드 분석 결과 |
| **참여자 신원·등급** | 이름·연락처·생년월일·연구실별 익명 코드·누적 참여 횟수·등급 |
| **예약** | 한 사람이 어떤 실험의 어떤 슬롯에 들어왔는가, 다회차면 같은 그룹으로 묶임 |
| **참여자비 정산·청구** | 신분·계좌·서명·통장 사본 (암호화) · 정산 상태 · 청구 묶음 |
| **온라인 실험 진행** | 토큰·블록 진행도·완료 코드·연구자 확인 여부 (온라인 실험만) |

이 다섯 줄기는 **하나의 실험 식별자 (`experiments.id`)** 에서 모두 따라
내려갈 수 있도록 설계되어 있습니다. 외부 연동 (캘린더·메일·문자·외부
미러)·자동 정기 작업·암호화·접근 권한 같은 보조 장치들이 이 다섯 줄기를
뒷받침합니다.

## 1. 실험

### 무엇이 기록되는가
실험을 만들면 한 행이 `experiments` 테이블에 만들어지고, 그 행에 모든
실험-수준 정보가 모입니다.

기본 정보:
- 제목, 기간 (시작일·종료일), 일일 가능 시간대, 회당 진행 시간, 회당 정원,
  세션 수, 참여자 보상, 실험 모드 (오프라인·온라인·하이브리드)
- 위치 — 미리 등록된 시설 목록 (`experiment_locations`) 중 선택
- 분류 태그 (행동·MRI·뇌자극·시선추적·온라인 등 — 여러 개 선택 가능)
- 모집 가능 요일 (월~일 중 선택), 모집 마감일

연구 메타데이터:
- **실험 코드 경로** (GitHub 주소 또는 연구실 서버 경로) · **결과 저장 경로**
  → 이 두 값이 비어 있으면 실험을 "활성" 상태로 전환할 수 없습니다 (DB
  자체에서 거부).
- **선언 파라미터** — {이름, 자료형, 기본값, 선택지} 형태 목록
- **사전 점검 체크리스트** — {항목, 필수 여부, 체크 여부, 체크 시각}
- **자동 분석 결과** — 등록된 코드를 자동으로 읽어내 조작변수·종속변수·자극
  클래스·무작위 시드 처리·counterbalance 등을 추정한 결과. 연구자가 검토·
  수정·확정한 라벨까지 같은 항목에 보관됩니다.
- IRB 문서 URL · 유의사항 · 프로토콜 버전 번호

리마인더 설정:
- 전날·당일 리마인더 켜기/끄기, 발송 시각, 발송 채널 — 모두 실험별로
  연구자가 자유롭게 설정합니다.

온라인 실험인 경우 추가로:
- 진입 URL, 시행 횟수, 블록 수, 예상 소요 시간, 완료 토큰 형식, counterbalance
  명세 등이 `online_runtime_config` 항목에 모입니다.

### 보조 테이블
- `experiment_locations` — 등록된 실험실 (이름·주소·지도 링크). 관리자만
  새 장소를 등록할 수 있습니다.
- `experiment_manual_blocks` — 연구자가 특정 시간대를 수동으로 차단해 두는
  표시. 슬롯 그리드를 만들 때 캘린더 점유 시간과 함께 빠집니다.
- `experiment_online_screeners` (+ 응답 테이블) — 온라인 실험에서 참여 전에
  답해야 하는 질문 목록과 적격 조건.

### 안전장치
- 코드 경로 / 저장 경로 미입력시 활성화 거부 (DB 트리거).
- 사전 점검 체크리스트의 필수 항목이 모두 체크되지 않으면 새 예약을
  받지 않음.
- 자동 분석 결과는 *연구자가 확정한 라벨*만 최종 보관됨 — 자동 분석기의
  정확도는 보장하지 않습니다.

### 누가 무엇을 볼 수 있는가
- 누구나 활성 실험을 읽을 수 있습니다 (모집 페이지에 노출되어야 하므로).
- 연구자는 자기가 만든 실험만 수정할 수 있습니다.
- 관리자는 모든 실험을 봅니다.

## 2. 예약

### 무엇이 기록되는가
한 슬롯을 한 사람이 잡으면 한 행이 `bookings` 테이블에 만들어집니다.
다회차 실험이면 같은 사람이 같은 그룹 식별자 (booking_group_id) 아래 여러
행을 갖습니다.

각 예약 행에 모이는 것:
- 어떤 실험, 어떤 참여자, 슬롯 시작·종료 시각
- 회차 번호 (single-session이면 1, 다회차면 1·2·3…)
- 같은 참여 묶음의 그룹 식별자 (다회차를 묶기 위함)
- 참여자 번호 (Sbj #) — 실험 단위로 1, 2, 3 … 식으로 순서대로 부여
- 상태 — 확정 · 취소 · 완료 · 노쇼 · 진행중
- 공유 캘린더에 등록된 이벤트 식별자
- 외부 미러 페이지 식별자 (선택)

`participants` 테이블에는 이름·연락처·이메일·성별·생년월일이 들어갑니다.
한 사람이 여러 실험에 참여해도 같은 한 행으로 합쳐집니다 (연락처와 이메일
조합으로 식별).

### 핵심 안전장치 — 동시 예약 차단
같은 슬롯에 두 사람이 *동시에* 제출하면 한 명만 통과합니다. 데이터베이스가
다음을 한 묶음으로 처리하기 때문입니다.

1. 실험이 활성 상태인지 확인
2. 등록 마감일 통과 안 했는지 확인
3. 이 슬롯이 허용 요일에 들어있는지 확인
4. 같은 사람이 이미 같은 실험에 예약했는지 확인 (중복 참여 차단)
5. 다회차면 정확한 회차 수가 맞는지 확인
6. 실험 단위로 잠금을 걸어 동시 예약을 직렬화
7. 슬롯 정원이 가득 차지 않았는지 확인
8. 참여자 정보를 새로 추가하거나 기존 행과 합침
9. **블랙리스트 차단** — 해당 연구실의 등급이 'blacklist'이면 예약 거부
10. 참여자 번호 부여, 예약 행 삽입
11. 리마인더 일정 행을 만들고 후속 연동 큐를 적재
12. 정원이 차면 실험을 자동으로 "완료" 상태로 전환 (auto-lock 옵션)

이 모든 단계가 한 묶음으로 성공해야 예약이 확정됩니다. 중간 어디서든
실패하면 전체가 취소되어 어떤 상태도 어중간하게 남지 않습니다.

### 후속 연동 큐 — booking_integrations
예약이 확정되면 외부 시스템 (공유 캘린더 · 외부 미러 · 이메일 · 문자)에
보낼 작업이 이 테이블에 한 행씩 적재됩니다. 30분마다 정기 작업이 미처리
행을 가져가 처리하고, 실패하면 시간 간격을 늘려가며 최대 5회까지 재시도
합니다. 한 번 처리에 성공한 행은 다시 처리되지 않습니다.

### 리마인더 일정 — reminders
예약 확정 시 리마인더 일정 행이 만들어집니다. 발송 시각이 도래하면 15분마다
도는 정기 작업이 가져가 실제 발송합니다. 실험별 설정 (켜기/끄기, 시각, 채널)
이 그대로 반영됩니다.

## 3. 참여자 · 등급

### 신원
한 사람은 `participants` 테이블에 한 행. 이름·연락처·이메일·생년월일.
연락처 + 이메일 조합으로 중복을 식별합니다.

### 연구실별 익명 코드
같은 사람이라도 *연구실에 따라 다른 익명 코드*를 갖습니다
(`participant_lab_identity`). 외부 미러 페이지나 엑셀 보고서에는 이 익명
코드만 노출되고, 이름은 절대 나가지 않습니다. 익명 코드는 연구실 별 비밀값
(salt) 을 이용해 만든 해시이므로 외부에서 다른 연구실의 참여자와 같은
사람인지 추정할 수 없습니다.

### 등급
완료된 예약 수가 누적되면 등급이 자동으로 갱신됩니다 (`participant_classes`).

- **newbie (신규)** — 기본
- **royal (단골)** — 일정 횟수 이상 완료 시 자동 승격
- **vip / blacklist (특별 관리)** — 관리자가 수동으로만 부여 (자동 변환
  대상 아님)

등급이 바뀔 때마다 한 행이 추가되며, 옛 행은 그대로 남아 변경 이력
(`participant_class_audit`)이 누적됩니다. 즉 *언제* / *왜* / *누가*
바꿨는지가 영구적으로 보관됩니다.

자동 승격이 일어나면 시스템이 해당 연구자에게 안내 메일을 발송할 수
있으며 (`class_promotion_notifications`), 같은 승격 건이 두 번 알리지는
않도록 발송 이력이 함께 기록됩니다.

## 4. 참여자비 청구

### 무엇이 기록되는가
한 참여 묶음 (booking_group)에 대해 한 행이 `participant_payment_info`에
만들어집니다. 다회차 실험이라도 한 사람당 한 행입니다.

각 정산 행에 모이는 것:
- 신분 정보 — **암호화 저장**. 평문은 데이터베이스 어느 곳에도 없습니다.
  복호화 키는 운영 환경 변수에만 있어 화면에는 절대 노출되지 않습니다.
- 계좌 정보 — 은행·계좌번호·예금주·기관명 (평문)
- 서명·통장 사본 — Supabase 첨부 보관소에 보관, 정산 행은 경로만 갖고
  있습니다. 첨부 보관소는 비공개이며 해당 실험의 연구자만 읽을 수 있습니다.
- 활동 기간 — 슬롯 시각의 최소·최대로 자동 계산
- 정산 금액 (원) — 자동 계산되며, 연구자가 수동 조정하면 그 사실이 표시됩니다.
- 일회용 입력 링크의 토큰 해시·발급 시각·만료 시각·폐기 시각
- 상태 — 다음 다섯 단계 중 하나
  - *pending_participant* — 참여자 입력 대기
  - *submitted_to_admin* — 참여자가 제출 완료
  - *claimed* — 연구자가 청구 묶음 생성
  - *paid* — 행정실 지급 완료
  - *paid_offline* — 시스템 외부에서 지급 처리

### 상태 전이 안전장치
- 정산 행은 사전 정의된 순서로만 상태가 바뀝니다. 한 번 *claimed* 된 행이
  다시 *submitted_to_admin* 으로 돌아가지 않습니다.
- 같은 행을 두 번 청구할 수 없도록 상태 전이가 DB 차원에서 잠겨 있습니다.

### 청구 묶음과 양식 파일
연구자가 여러 참여자를 한 묶음으로 청구하면 `payment_claims` 에 한 행이
만들어지고, 묶음에 포함된 정산 행들의 상태가 한꺼번에 *claimed* 로 바뀝니다.
양식 파일이 생성될 때마다 `payment_exports` 에 한 행이 누적되어 *언제 누가
어떤 묶음을 생성했는가* 가 영구 기록됩니다.

연구자가 행정실 발송 버튼을 누르면 `payment_claims` 행에 발송 시각·받는
사람·발송 식별자가 박혀, 추후 어떤 청구가 언제 누구에게 갔는지 조회할
수 있습니다.

### 입력 폼의 보안
참여자에게 보낸 정산 폼 링크는 *일회용 + 만료 시각 + 폐기 가능* 입니다.
참여자가 제출하는 순간 토큰이 폐기되어 같은 링크로 다시 들어갈 수 없습니다.
신분 정보는 입력 즉시 암호화되며 평문은 디스크에 도달하지 않습니다.

## 5. 온라인 실험 진행 (해당 실험만)

오프라인 실험은 이 도메인이 없고, 온라인·하이브리드 실험에만 적용됩니다.

`experiment_run_progress` 에 한 예약당 한 행이 만들어집니다.

기록되는 것:
- 일회용 토큰의 해시·발급 시각·폐기 시각
- 제출된 블록 수, 마지막 블록 시각
- 완료 코드 (참여자에게 화면에 표시됨) · 발급 시각
- 연구자 확인 여부 · 확인 시각
- 시도 제한 — 1초당 최대 1회, 분당 최대 100회 제출 가능. 초과 시 잠금
- 잘못된 확인 시도 누적 카운트 + 잠금 시각 (무차별 대입 방지)
- 파일럿 여부 (파일럿 행은 참여자 번호를 소비하지 않음)
- counterbalance 자동 배정 결과 (예: 'A'·'B')
- 주의 실패 횟수, 행동 신호 — 포커스 이탈 횟수, 붙여넣기 횟수, 평균 타이핑
  간격 등 *집계값만* (원문은 절대 저장하지 않음, 참여자 동의 필요)
- 진입 URL의 무결성 해시

연구자는 이 행에서 *확인 시각·확인자* 두 항목만 수정할 수 있습니다.
나머지 컬럼은 시스템만 갱신합니다 (DB 차원의 권한 제한).

## 6. 운영 — 사용자·권한

### profiles
인증된 사용자 한 명당 한 행. `auth.users` 의 보조 정보를 담습니다.

- 역할 — 관리자 또는 연구자
- 표시 이름 · 휴대전화 · 연락 이메일 (실제 메일과 별도 가능)
- 비활성 여부 — 비활성화하면 즉시 모든 접근이 차단됩니다.

사용자 가입 시 `auth.users` 에 행이 만들어지면 자동으로 `profiles` 행도
함께 만들어집니다 (DB 트리거).

### registration_requests
관리자가 직접 만들지 않은 사용자는 가입 신청 페이지에서 사용자명·표시 이름·
비밀번호를 제출합니다. 비밀번호는 즉시 암호화되어 보관되며, 관리자 승인 후
실제 계정이 만들어질 때 복호화되어 사용됩니다. 승인/거부 결과·시각·처리자가
기록됩니다.

### labs
다른 연구실에서 본 코드를 가져갈 때 한 행이 만들어집니다 (현재 운영 중인
시스템은 한 연구실용). 각 연구실은 *자기만의 비밀값* 을 갖고 있어 익명 코드
생성에 사용됩니다.

## 7. 외부 연동 / 캐시 / 감사 (보조 family)

### 외부 연동 큐 — booking_integrations
앞 §2 에서 설명. 한 예약에 대해 외부로 나가는 모든 작업 (공유 캘린더·외부
미러·이메일·문자·온라인 진행 상태 이메일 등)이 한 행씩 이 테이블에서
대기·처리·재시도됩니다.

### 캘린더 빈 시간 캐시 — calendar_freebusy_cache
공유 캘린더의 빈 시간 조회 결과를 캐시. 참여자가 슬롯 그리드를 볼 때 매번
외부 API를 호출하지 않도록 합니다. 실험을 만들거나 수정하면 관련 캐시가
무효화됩니다.

### 알림 발송 이력 — notification_log + reminders
한 알림 행 (`reminders`) 에 대해 실제 발송 시점에 결과가 `notification_log`
에 누적됩니다. 어떤 채널 (메일·문자) 로 보냈는지, 외부 시스템 식별자 (이메일
메시지 ID 등), 실패 사유 등이 보관됩니다.

### 외부 미러 정상상태 — notion_health_state
외부 지식베이스 미러 (`Lab DB` 의 외부 동기화 부분; 현재 부분 구현)가
정상적으로 동작하는지 정기 점검하고 그 결과를 누적. 스키마가 어긋났는지,
실패한 행이 몇 개 회복됐는지 등.

### 메타데이터 누락 리마인더 이력 — metadata_reminder_log
매주 월요일 오전 9시에 발송되는 *연구자 대상 메타데이터 누락 안내*가 언제
누구에게 어떤 항목으로 발송됐는지가 누적됩니다. 같은 연구자에게 너무 자주
보내지 않도록 시간 간격이 제한됩니다.

### 승격 알림 이력 — class_promotion_notifications
참여자가 등급 자동 승격되었을 때 연구자에게 안내하는 메일의 발송 이력.
같은 승격 건에 대해 두 번 알리지 않도록 가드합니다.

## 8. 일반적인 데이터 흐름 (시나리오 4가지)

### A. 한 사람이 한 실험에 예약하기까지
1. 연구자가 실험 정보 입력 → `experiments` 행 생성
2. 코드 경로 입력 + 자동 분석 후 연구자가 확정 → `experiments` 의 분석 결과
   항목 갱신
3. 사전 점검 완료 → `experiments` 의 체크리스트 완료 시각 박힘
4. 모집 공개 토글 → `experiments.status = 'active'`
5. 참여자가 슬롯 선택 → DB 함수 `book_slot` 호출
6. 검증 + 잠금 + 정원 확인 + 블랙리스트 확인 후 `participants` 와 `bookings`
   에 행이 한꺼번에 들어감
7. `booking_integrations` 에 캘린더 · 미러 · 이메일 · 문자 행이 적재됨
8. `reminders` 에 전날·당일 리마인더 행이 적재됨
9. 정기 작업이 후속 행들을 처리해 외부로 발송

### B. 실험 종료 후 청구
1. 슬롯 종료 시각 + 유예기간이 지나면 정기 작업이 예약 상태를 자동으로
   'completed' 로 갱신 (`bookings.auto_completed_at`)
2. 완료 트리거가 자동으로 동일 사용자의 등급을 재계산
3. 정산 안내 메일이 참여자에게 발송됨 — `participant_payment_info` 행이
   *pending_participant* 상태로 존재함을 확인
4. 참여자가 폼 작성 → 신분 정보 암호화 후 `participant_payment_info` 갱신,
   상태가 *submitted_to_admin* 으로 전이, 토큰 폐기
5. 연구자가 청구 → `payment_claims` 행 생성, 정산 행들이 *claimed* 로 전이
6. 양식 파일 생성 → `payment_exports` 행 누적
7. 연구자가 행정 발송 → `payment_claims` 의 발송 시각·받는 사람·메시지 ID
   박힘

### C. 자동 처리 정기 작업
- 매 15분: 발송 시각이 도래한 `reminders` 행을 가져가 실제 발송
- 매 30분: `booking_integrations` 의 미처리·실패 행을 정해진 횟수 한도
  안에서 재시도
- 매일 새벽 1시: 외부 미러의 스키마 어긋남 점검
- 매일 새벽 2시 15분: 종료 후 7일 지난 예약을 자동 완료 처리 + 참여자에게
  정산 안내 발송
- 매주 월요일 오전 9시: 메타데이터 누락된 실험을 연구자에게 안내

### D. 연구자 가입 → 승인 → 시작
1. 가입 신청 → `registration_requests` 행 생성 (비밀번호 암호화 저장)
2. 관리자가 승인 → 시스템이 `auth.users` 에 사용자 생성, 트리거가 자동으로
   `profiles` 행 생성
3. 연구자가 이메일 매직링크로 로그인 → `profiles.role` 에 따라 접근 권한이
   차등 부여됨

## 9. 일반적인 조회 패턴

### 한 실험의 모든 예약과 참여자 정보
```sql
select b.*, p.name, p.phone, p.email, e.title
from bookings b
join participants p on p.id = b.participant_id
join experiments  e on e.id = b.experiment_id
where b.experiment_id = ?
  and b.status = 'confirmed'
order by b.slot_start;
```

### 한 참여자의 현재 등급 (연구실별)
```sql
select class
from participant_class_current
where participant_id = ? and lab_id = ?;
```

### 정산 대기 중인 행 (한 실험)
```sql
select ppi.*, p.name, pli.public_code
from participant_payment_info ppi
join participants p on p.id = ppi.participant_id
left join participant_lab_identity pli
  on pli.participant_id = p.id and pli.lab_id = ?
where ppi.experiment_id = ?
  and ppi.status = 'submitted_to_admin'
order by ppi.submitted_at;
```

### 정기 작업이 처리할 미처리 외부 연동
```sql
select * from booking_integrations
where status = 'pending'
order by created_at
limit 100;
```

### 메타데이터가 누락된 활성 실험
```sql
select id, title
from experiments
where status = 'active'
  and (code_repo_url is null or btrim(code_repo_url) = ''
       or data_path is null or btrim(data_path) = '');
```

### 한 사람이 참여한 모든 실험 (외부 미러용 익명 코드 기준)
```sql
select e.title, b.slot_start, b.status
from bookings b
join experiments e on e.id = b.experiment_id
join participant_lab_identity pli
  on pli.participant_id = b.participant_id
  and pli.lab_id = ?
where pli.public_code = ?
order by b.slot_start;
```

## 10. 안전장치 요약

| 무엇 | 어떻게 |
|---|---|
| 동시 예약 차단 | DB 함수가 실험 단위 잠금을 걸어 직렬화 |
| 중복 참여 차단 | 같은 사람이 같은 실험에 두 번 못 들어옴 (DB 함수) |
| 활성화 게이트 | 코드 경로 / 저장 경로 미입력시 활성 거부 (DB 트리거) |
| 체크리스트 게이트 | 필수 항목 미완료시 새 예약 거부 |
| 신분 정보 암호화 | AES 기반 암호화. 키는 운영 환경 변수에만, 화면에 절대 노출 안 됨 |
| 토큰 일회용 | 정산 폼·온라인 진행 토큰은 해시 저장 + 만료 + 폐기 가능 |
| 더블 청구 차단 | 상태 전이가 DB 차원에서 잠겨 있음 |
| 외부 발송 확인 게이트 | 행정실로 가는 메일은 연구자 확인 모달 통과 후에만 |
| 블랙리스트 차단 | 등급이 'blacklist' 면 예약 자체가 거부됨 |
| 시도 제한 | 온라인 실험 토큰은 초당·분당 시도 한도 |
| 무차별 대입 방지 | 잘못된 확인 시도 누적 시 일정 시간 잠금 |
| 사용자별 권한 | 연구자는 자기 실험만 · 관리자는 전부 · 비활성 계정은 즉시 차단 |
| 외부 미러 가명화 | 외부로 나가는 식별자는 익명 코드뿐 (이름은 안 나감) |
